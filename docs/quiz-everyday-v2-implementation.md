- 기준일: 2026-11-06

- 전제 연구 문서: docs/retreat-taxonomy-and-quiz-v1.md
- 원칙: main 및 공개 홈페이지 수정 금지, 별도 브랜치에서 구현·검증 후 승인

## 1. UX 목표
**일상적이고 재미있는 질문 → 뜻밖에 공감되는 결과 → 실제 피정 발견 → 위로·말씀·성인·묵상의 작은 피정.**
질문에서 성경/영신수련/관상 같은 용어를 앞세우지 않는다. 사용자에게 특정 영성을 추정해 단정하지 않는다. 예를 들어 책을 좋아하는 취향은 '읽기·사색'의 약한 단서이며 성경 읽기 선호의 증거가 아니다. 10문항 결과는 임상적 심리평가가 아니다.

1~8번은 마음·취향·진행 방식, 9번은 시간, 10번은 동행 형태. 지역·날짜·예산·대상 연령 등은 **결과에서 선택적으로 조정**한다. 결과 순서는 **유형 한 줄 → 실제 추천 피정 최대 3개 → 필터 조절 → 위로·성경 장절·검증된 성인·묵상 질문·기도**.

## 2. 태그 사전 및 가중치
각 답변에 아래 feature 1~3개를 연결. 가중치 1=약한 단서, 2=중간, 3=강한 선호. 값을 절대적인 신앙 수준/성격 점수로 표현하지 않는다.
- needs: rest(쉼), reflect(성찰), reconcile(화해), discern(식별), renew(새출발), connect(교류), learn(배움), comfort(위로)
- styles: solitude(혼자 집중), read(읽기·기록), silence(침묵), guided(안내), talk(대화), group(함께), movement(걷기·체험), creative(음악·창작), ritual(규칙적 시간표), flexible(자유 시간)
- 8문항에 걸쳐 한 feature가 과도하게 쌓이지 않도록 누적을 6점으로 제한. '건너뛰기'는 feature 점수 0.
- 특징/감정 선호 feature와 이냐시오/가르멜/베네딕도/성령쇄신 같은 **기도 전통 태그는 별개**. 특정 전통 선호는 결과의 선택형 관심 칩으로만 강하게 적용.

## 3. 열 가지 질문과 정식 선택지 (문구와 ID 모두 고정)

- q1_b: "그럼 어디라도 나가볼까?" → movement:2, renew:1

- q9_b: "주말의 1박 2일." → durationPreference: oneNight
- q9_c: "2~3박 정도도 괜찮아요." → durationPreference: twoThreeNights
- q9_d: "4박 이상 길게 머물 수도 있어요." → durationPreference: long

### Q10. 이번에는 누구와 떠나고 싶나요?
- q10_a: "혼자." → partyPreference: solo
- q10_b: "친구나 지인과." → partyPreference: friends
- q10_c: "배우자와." → partyPreference: couple
- q10_d: "부모님·자녀 등 가족과." → partyPreference: family
- q10_e: "본당·단체 사람들과." → partyPreference: group
- q10_f: "아직 모르겠어요." → partyPreference: undecided
- 주의: 혼자 간다고 공동체 피정 참가 불가한 것은 아님. 배우자 동행이 곧 부부 전용 프로그램만을 뜻하는 것도 아님. 주최 측 실제 신청 규칙 확인.

모든 질문은 1개 답변 선택, '잘 모르겠어요/건너뛰기', '이전 질문' 가능. 답변 바꾼 뒤 점수와 결과 재계산. 10문항 진행 중 화면이 맨 위로 점프하지 않아야 함.

## 4. 피정 유형 매핑 (제약과 구분)
- rest → 쉼·자유·휴식형. 장기 대침묵을 쉼 피정으로 자동 연결하지 않음.
- reflect/read → 묵상·영성 독서·렉시오 디비나·성경 강의 **약한 연결**. read만으로 성경/교리 강의 확정 금지.
- silence/solitude → 개인·관상·침묵; 개인 피정과 '완전 대침묵'은 다른 속성.
- connect/talk → 나눔·영적 동반·관계 피정. 관계 피정은 반드시 집단 나눔이라는 가정 금지.
- reconcile → 화해·용서 주제. 사용자에게 상처/죄책감 진단 금지.
- discern → 삶의 선택/식별. 영신수련·성소 전용은 프로그램 실제 대상 자격 별도 확인.
- learn/guided → 성서연수·강의·초심자 기도 안내.
- movement/creative → 걷기·생태영성·음악·창작·체험. 단순 산책과 순례/생태영성은 별도 태그.
- group → 공동체 나눔·기도·찬양. 성령쇄신이라고 단정 금지.
- ritual → 정해진 시간표·전례형 (미사·성체조배 선호 자체는 묻지 않았으므로 자동 확정 금지).

전국 피정 유형은 **하나의 고정 카테고리 대신 프로그램에 여러 태그**를 허용한다. 분류 축: (A) 목적/삶의 주제 (B) 기도/영성 전통 (C) 운영 방식 (D) 대상 및 필수 자격 (E) 회차 및 모집 정보. 기존 v1.0 조사 문서의 전체 범주와 소스 목록 유지. 수집된 실제 프로그램이 이 구조에 없는 경우 운영자가 새 태그를 검토 후 추가 가능.

### 결과 화면의 선택형 관심 칩 (10문항에 추가 질문 강요 금지)
말씀·성경 / 침묵·관상 / 영신수련 / 미사·성체조배 / 찬양·성령 / 가족·관계 / 수도생활 / 생태영성 / 아직 잘 모르겠어요

이를 누를 때는 프로그램의 실제 확인된 영성 태그에만 강한 가점 부여. 임의로 신앙 성향을 추측하지 않음. 별도 날짜·지역·예산·연령·숙박 조건 필터는 선택적, 결과 화면에서 수정 가능.

## 5. 추천 알고리즘 명세

### ① 후보
미래 또는 진행 중인 실제 회차가 있으며 공식 문의/신청 경로가 등록된 프로그램. 지난 회차/명확한 모집 마감은 '신청 가능' 추천에서 제외. 모집 예정은 '접수 예정'으로 표시.

### ② 우선 지켜야 할 조건
- 사용자와 프로그램에 **명시된** 연령·대상·동행 형태·선행 경험·단체 전용·접근성·지역·날짜·예산 조건은 무시하지 말 것.
- 연령 등 사용자 정보가 없으면 부적격으로 단정하지 말고 '참가 대상 확인 필요'. 미성년자와 성인 전용 간 명확한 충돌은 제외.
- 모집 중/남은 좌석은 주최 측 직접 연동되어 최신 확인된 경우에만 단정, 그 외 '주최 측 확인 필요'. 접수 요청을 '예약 확정'으로 표시 금지.
- 시간(Q9)은 선호를 우선 적용하고, 결과 필터에서 '이 기간만' 명시한 경우에만 엄격 적용.
- '배우자·가족' 선호는 자격/정원이 확인되는 경우만 한정, 일반 피정도 관계자들이 같이 신청 가능하면 남겨 둠.
- 민감한 답변(슬픔·화해 등)을 병명이나 위험 판정으로 해석하거나 저장하지 않는다.

### ③ 점수 (초기 가중치, 정확도 보증 아님)
- 답변의 특징 점수 합산, 동일 특징의 누적 상한 6.
- 확인된 목적 태그 일치 건당 +2 (목적 최대 +8).
- 확인된 운영 방식 태그 일치 건당 +2 (방식 최대 +8).
- Q9 기간 선호 일치 +4 / 약한 불일치 -2; '유연'이면 0.
- Q10 동행 적합 +4 / 약한 불일치 -2. 명확한 불허 조건은 배제.
- 영성 관심 칩과 프로그램의 **검증된** 실제 기도 태그 일치 시 +6.
- 장기 대침묵에 편안함이 없는 답변 조합, 나눔 선호 등과 큰 충돌이 있으면 -4의 소프트 감점.
- 동점일 때 더 가까운 유효 회차 우선. 유명 수도회·별점·광고를 편향 가중치에 넣지 않음.
- **서로 다른 목적/수도회가 골고루 나올 수 있도록** 적합성을 크게 손상시키지 않는 범위에서 상위 3개 다양화.

### ④ 추천 이유 생성
선택 답변의 실제 특징 + 프로그램 공식 설명에서 확인된 형식을 묶어 한 문장.
좋은 예: '혼자 생각을 정리하는 시간을 선호하셨고, 이 피정에는 개인 묵상 시간이 있습니다.'
금지: '당신은 상처가 깊어서 치유 피정이 필요합니다.' / 공고에 없는 면담이나 활동을 꾸며내는 것.
근거 불충분하면 '또 다른 머뭄 방식도 함께 살펴보세요.'로 정직하게 표시.

### ⑤ 0~3개만 실제 표시
후보가 0개이면 없음 안내+조건 넓히기+전국 검색으로 이동. 1~2개이면 있는 만큼만 표시. 프로그램명, 위치, 비용, 연락처, 모집 상태, 확인 시각이 불명확하면 '확인 필요'로 명시. 가상 12개는 **가상 시연**으로만 사용.

## 6. 결과 UI 순서
1. '지금 당신에게 어울리는 머뭄' - 닫힌 성격진단처럼 말하지 않는 짧은 유형+위로 한 줄.
2. 가장 상단에 실제 추천 머뭄•피정 최대 3개, 사진·날짜·대상·지역·비용·모집상태·공식 신청 경로·추천 이유.
3. 선택형 필터: 날짜, 지역, 예산, 참가자 연령, 숙박 여부, 영성 관심 칩. 수정 즉시 결과 목록 갱신(퀴즈 재시작 불필요).
4. '짧은 머뭄' - 위로 → 가톨릭 새번역의 확인된 성경 장절·공식 링크 → 검증된 성인 → 묵상 질문 → 기도.
5. 내 서랍 저장·공유·다시 시작.
- 결과 공유 카드에 상세 답변 등 민감 정보를 포함하지 않음.
- 답변은 기본적으로 서버에 저장하지 않음. 계정 저장은 명시적 동의.
- 질문 중에는 현 위치에서 질문과 선택지만 바뀌게, 마지막 결과는 자연스럽게 결과 시작점으로.
- 어르신 사용성: 홈의 '오늘, 1분 머뭄'은 기본 펼침으로 하고 '+' 필수 클릭 구조 제거.

## 7. 데이터 구조 지시
질문은 별도 상수/데이터 파일로 관리:
questions = [{id, prompt, options:[{id,label,features,durationPreference?,partyPreference?}]}].
사용자 선호 = {featureTotals,durationPreference,partyPreference,selectedInterests,filters}.
프로그램 = {id,title,organizationId,venueId,purposeTags[],prayerTraditionTags[],formatTags[],audienceEligibility,officialContact,officialApplyUrl}.
회차 = {id,programId,start,end,fee,priceUnit,applicationStart,applicationEnd,eligibilityOverrides,registrationState,verifiedAt,source}.
현재 프로젝트 구조는 index.html + assets/js/app.js + assets/js/data.js + assets/css/* 이므로 기존 파일을 무작정 전면 재작성하지 말고 퀴즈·추천 함수를 분리해 연결한다. 실제 수도회가 등록할 때 태그·대상·회차 정보를 추가할 수 있어야 한다.

## 8. 구현 후 검증 사례 (전부 통과해야 반영)
1. Q1~Q10 답변·건너뛰기·이전·수정·다시 시작에 오류가 없음.
2. 375/390/430px 모바일과 PC에서 질문 클릭마다 페이지 맨 위로 점프하지 않음.
3. '책/영화' 선호로 성경/이냐시오/가르멜 피정을 확정해서 과도하게 추천하지 않음.
4. 쉼+하루 선호 → 30일 숙박형 프로그램이 최상위로 뜨지 않음.
5. 길찾기+장기 가능+지도 선호+영신수련 칩 → 영신수련 상위 후보, 선행 경험은 별도 확인.
6. 관계+배우자 동행 → 부부 전용 또는 부부가 함께 가능한 피정, 모녀 전용은 제외.
7. 가족 동행 → 가족 참가 조건 확인; 개인 전용이 아닌 일반 피정도 허용 조건에 맞게 노출.
8. 청소년 연령 필터 → 성인/성소 전용 중 부적격 프로그램 제외.
9. 나눔 선호와 대침묵 간 불일치 소프트 감점, 선호만으로 전체 배제하지 않음.
10. 출퇴근/온라인만 선호하면서 '이 조건만' 필터 → 숙박 전용 피정 제외.
11. 마감/지난 회차 제외, 최신 확인 불가에는 모집상태 '주최 측 확인 필요'.
12. 후보 0/1/2/3개 각각 가상으로 채우지 않고 정확히 표시.
13. 결과에서 추천이 묵상보다 앞, 말씀·성인·기도 내용 삭제 금지.
14. 네 가지 탐색·서랍·1분 머뭄·수도회 등록·일정·QR 시연 기존 기능 회귀 테스트.
15. 수엘 추가 금지, 미확정 CAMUM/GAMUM 로고 임의 변경 금지.
16. 가상 데이터는 실제 수도회나 신청 링크로 오인되지 않음.

## 9. 최종 판정
**이 문서는 Codex가 구현할 수 있는 질문·분류·추천·테스트의 완결된 v2.0 명세다.**
하지만 실제 공개 서비스의 정확한 추천은 실제 수도회 프로그램 등록, 모집 상태 연동, 다양한 연령의 사용자 체험 검증을 거쳐야 완성이다. 따라서 문서를 완성했다는 사실을 실제 추천 성능의 입증으로 주장해서는 안 된다.

**main / GitHub Pages를 바로 변경하지 말고**, 별도 구현 브랜치에서 모든 테스트 후 사용자가 보고 승인한 경우에만 병합한다.
