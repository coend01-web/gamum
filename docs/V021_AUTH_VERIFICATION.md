# CAMUM v0.21 개발 인증 검증 — 2026-11-11

공개 main/v0.2 및 GitHub Pages는 변경하지 않았다. 개발 브랜치는 `feature/v0.21-convent-ops`, 실제 검증 프로젝트는 `qzxdxqrdulkfoktkmkly`이다. 기존 DB를 재설치하거나 명부를 다시 가져오지 않았다.

## 완료한 연결

- 사용자가 Supabase Auth에서 직접 이메일·비밀번호를 설정한 중앙관리자 1명을 `camum_private.operators`에 명시적으로 등록했다. 일반 기관 자격정보와 분리되어 있다.
- 사용자가 인증 앱으로 TOTP를 등록·검증했다. 실제 DB의 verified TOTP 1건과 실제 관리자 화면 진입을 확인했다. 비밀번호·QR·OTP를 보고서나 저장소에 기록하지 않았다.
- `institution-auth`를 Supabase CLI의 서버측 번들 배포로 개발 프로젝트에 배포했다. 서버 전용 비밀값과 정확한 허용 출처(`http://127.0.0.1:8771`, `http://localhost:8771`)를 설정했다. 임의 출처는 403, 인증 없는 관리자 요청은 401로 거부됐다.
- 공개 publishable key만 로컬 브라우저 연결에 사용한다. 기관 최초 설정/복구는 MFA 중앙관리자와 승인된 기관 확인 기록이 있어야 일회용 링크를 발급한다. 기본 공용 비밀번호는 없다.

## 발견하고 수정한 오류

SDK 2.119.0이 이미 `data:image/svg+xml;utf-8,`를 붙여 반환하는 QR에 화면 코드가 다시 접두사를 붙여 이미지가 깨졌다. SVG 본문을 한 번만 인코딩하도록 수정했다. 새로고침 후에는 같은 앱의 미완료 TOTP만 정리하고 다시 등록하며, 검증된 인증 수단은 삭제하지 않는다. QR은 모바일 폭에 맞게 표시한다.

MFA 회귀 검사 9개를 추가했고 기존 전체 자동 검사를 통과했다. 실제 브라우저에서 QR 이미지 로드(219×219)와 사용자의 최종 MFA 완료를 확인했다.

## 실제 서버 검증

테스트용 임시 중앙관리자는 실제 Auth 비밀번호 로그인과 TOTP 검증을 거쳤다. JWT를 위조하거나 MFA를 우회하지 않았다. 검사 후 임시 관리자 권한을 회수하고 계정을 비활성화했다. 실제 중앙관리자 1명만 남았다.

- AAL1 상태의 중앙관리 권한 거절 → TOTP 검증 후 AAL2 관리자 허용.
- 가상 A/B 기관 생성·승인 → 관리번호 발급 → 일회용 링크를 통한 초기 비밀번호 설정 → 기관번호 로그인 성공.
- A→B 및 B→A 프로그램 조회·회차 수정 차단. 일반 기관의 중앙 명부 검색과 다른 기관 비밀번호 발급 거절.
- 기관 자체 승인 거절. 미승인 프로그램 카탈로그 제외, 중앙 공개 승인 후 40회차 반영, 1회차 조기마감 반영.
- 비밀번호 변경 후 이전 비밀번호 거절, 기존 JWT 조회 차단, 새 비밀번호로 재로그인 시 40회차 유지.
- 관리번호만으로 복구 토큰 발급 불가.

## 실제 브라우저 검증

`?sandbox=1` 없이 실제 개발 Supabase에 연결해 검사했다. 인증 앱은 사용자가 직접 설정했고, 자동검사에서는 생성된 가상 기관의 기존 비밀번호로 로그인했다.

| 화면 | 수행 및 결과 |
|---|---|
| PC 1280×900 | A 기관 로그인, 프로그램 초안 작성, 3개 주간 반복 회차 미리보기·저장 성공 |
| 모바일 크기 390×844 | B 기관 로그인, A 자료 미노출, 시설·프로그램 작성, 2개 반복 회차 미리보기·저장 성공 |
| 360px / 768px | 운영실 화면 가로 넘침 없음 |
| 새로고침 | B 기관 프로그램 1개·회차 2개 유지 |

모바일 검증은 데스크톱 브라우저의 모바일 화면 크기 검사이며, 실제 iOS/Android 기기 실험을 뜻하지 않는다.

## 검사 후 상태

가상 기관 2개는 이용 중지, 자격정보 2개는 disabled, 검사용 세션은 회수했다. 프로그램 3개·회차 45개는 삭제하지 않고 보관했다. 공개 프로그램은 0개이다. 실제 CBCK 기관은 가입 승인/관리번호 활성화하지 않았다. 명부는 고유 914건·기관 후보 162개·시설 후보 190개를 유지한다.

## 사용 방법과 남은 일

- 중앙관리자 개발 화면: `http://127.0.0.1:8771/ops/index.html` (이 컴퓨터의 로컬 서버가 켜져 있을 때만 열림).
- 실제 기관을 활성화하려면 중앙관리자가 공식 연락처로 담당 권한을 확인하고 출처 검토·가입 승인을 마친 뒤 초기설정 링크를 전달한다. 담당자는 자기 기관을 확인하고 비밀번호를 직접 정한다.
- 초기설정 링크 전달·공식 연락처 확인은 수동 운영 절차다. 자동 이메일 발송은 연결하지 않았다.
- 중앙관리자 인증 앱 분실에 대비한 별도 복구 운영 절차와 실제 모바일 기기 검사는 정식 운영 전에 마련해야 한다.
- v0.21은 여전히 개발판이며 정식 배포에는 별도 사용자 승인이 필요하다.

## 재검사

`npm test`는 로컬 회귀 검사다. `tests/ops-hosted.mjs`는 실제 Auth/Edge/RLS 검사용이며 별도 개발 환경 쓰기 동의가 있어야 실행한다. 인증된 MFA 관리자 클라이언트를 받는 `runHostedChecks()`도 제공해 사용자의 실제 비밀번호나 OTP를 자동 검사에 복사할 필요가 없도록 했다. 브라우저 검사용 fixture 유지 콜백 사용 시 호출자가 종료 후 해당 가상 기관을 반드시 중지하고 세션을 회수한다. 일반 CLI 실행은 검사 후 가상 기관을 중지한다.
