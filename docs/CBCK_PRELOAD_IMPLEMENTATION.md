# CBCK 사전등록 구현·검증 현황 — 2026-11-09

**작업 브랜치만 변경. 개발 Supabase 연결·프로젝트 식별 전이므로 실제 클라우드 등록은 미실행. 공개 v0.2/main 변경 없음.**

## 자료 검토

공식 목록 5개를 끝까지 대조: 남자 224, 여자 500, 피정·기도의 집 190, 본부 분류 남자 50·여자 112. 고유 CBCK code는 **914개**이며, 전체 목록과 본부 목록에 중복 등장하는 162개 분류를 포함한 원천 행은 **1,076개**다. 관리자 기본 목록은 같은 code의 본부/전체 기록을 묶어서 914개로 보여준다. 원천 기록과 예약 번호를 삭제하지 않는다.

기관 후보 **162개**, 시설 후보 **190개**. 괄호를 제외한 수도회명이 같은 **9개 묶음**은 자치 수도원·관구가 포함될 수 있어 자동 병합하지 않았다. 분원에는 새 관리번호를 부여하지 않는다. 중앙관리자가 동일 운영 주체라는 근거를 남기고 병합할 때도 기존 예약 번호는 폐기 예약으로 보존하고 재사용하지 않는다.

190개 시설 상세 페이지의 `책임수도회`와 CBCK 매일미사 피정 안내를 대조했다. 정확한 운영기관명 또는 괄호를 제외한 이름이 **단일 본부 후보**에 대응하고 두 자료가 충돌하지 않는 **87개**는 `source_matched`로 연결했다. **103개**는 운영기관 미명시, 본부 후보 부재, 여러 관구/수도원 또는 출처 간 표기 차이 때문에 검토 대상으로 남겼다. 단순 `소속 교구`는 직영 운영 근거로 사용하지 않는다. `source_matched`는 현재 담당 권한·가입·제휴 확인을 뜻하지 않으며 시설 활성화에는 중앙관리자의 추가 확인이 필요하다.

출처: https://directory.cbck.or.kr/OnlineAddress/Default.aspx 및 https://missa.cbck.or.kr/Retreat (페이지 표시 수정일 2026-01-26). 개별 근거 URL·확인일·판단은 Git에서 제외한 `private/cbck/directory_review.json`에 있다. 이름/기관 관계/출처만 저장하고 책임자 이름·개인 연락처는 수집 결과에 저장하지 않는다.

## 구현한 흐름

- `0004_directory_claims` 마이그레이션: 중앙관리자 MFA를 검사하는 검색·상세·검토·가입 승인 RPC. 원천 staging/신청/검토 기록은 private 스키마에 두며 anon/일반 기관은 직접 조회하거나 변경할 수 없다.
- 미가입 기관 검색, 연결 시설, 출처·검토 상태, 중복 후보 병합, 검증 이력, 가입 신청 검토. 조건 없는 전체 명부 공개 API는 없음.
- 가입 신청은 자기 기관 CBCK 상세 주소와 회신용 기관 연락처만 입력. 목록 전체를 노출하지 않으며 접수 사실만 답한다. 신청 연락처만 믿지 않고 중앙관리자가 기존 공식 연락처로 담당 권한을 확인해야 승인 가능하다.
- 독립 기관 검증 + 실제 가입 신청 + 담당 권한 확인 기록이 있어야 예약 관리번호로 `organizations` 등록. 이 단계는 비밀번호나 Auth 사용자를 생성하지 않는다.
- 중앙관리자가 확인한 기관만 일회용 설정 링크를 발급. 담당자는 링크에 고정된 자기 기관·번호·등록 시설을 확인하고 비밀번호만 설정한다. 다른 기관 선택 없음. 30분 만료·재사용 차단, 중지된 기관은 설정 차단. 최초 설정 완료 후 `claimed` 표시.
- 시설은 운영기관 소속을 확인하고, 해당 기관 가입 승인 및 실제 주소 확인 후 예약 시설번호로 등록. 시설 등록만으로 피정 프로그램은 공개되지 않는다.
- 기관/시설 예약 번호 충돌 시 전체 가져오기 중단. 원래 번호를 임의 변경하지 않으며, 번호 발급과 가져오기를 직렬화하고 신규 번호 생성기는 예약 번호를 건너뛴다.
- 재수집으로 사라진 원천 항목의 번호도 `code_reservations.json`에 계속 보존. 재가져오기 시 이미 중앙 검토하거나 활성화한 기록을 덮어쓰지 않는다. 이 기록의 출처 변경은 중앙 재검토가 필요하다.
- 명부 파일은 Git 제외. 신규 CI 실행에서는 명부 원본/SQL을 공개 다운로드 자료로 올리지 않는다. 로컬 시험 서버도 `/private/` 및 마이그레이션 경로를 제공하지 않는다.

## 검증 결과와 한계

- 기존 회귀·추천·CSV/반복·SQL/인증 검사 통과. 신규 명부/번호/기관 격리/MFA/가입 검사 **41개**, Edge 검사 총 **23개** 통과. Edge Auth는 가상 제공자이며 실제 Supabase 인증 검증과 구분한다.
- 삭제된 후보 번호가 재사용되지 않는 Python 회귀 검사 통과.
- 실제 명부를 로컬의 일회용 PostgreSQL 엔진에 반복 적용: **1,076행 / 고유 914건 / 기관 후보 162 / 시설 후보 190**, 중복 없음. 운영기관·Auth 계정 생성 **0**. 새 기관 번호 CAM-000163, 중앙 검토 기록 보존, 일반 기관·미로그인 접근 차단 확인.
- PC 1280px 및 모바일 390px 브라우저에서 가상 기관 검색→근거 검토→가입 승인→시설 소속 검증→시설 등록 확인. 모바일 가로 넘침 없음. A 기관에서 전체 명부 메뉴 비노출 확인.
- 실제 Supabase 프로젝트의 테이블 수·등록 수·RLS·Auth/Edge는 **아직 검증하지 못함**. 프로젝트 연결/로그인 전이므로 이번 작업의 실제 DB 쓰기는 **0건**이며, 대상 프로젝트에 이미 존재하는 자료 수는 알 수 없다.

macOS Python 인증서 저장소가 없으면 `SSL_CERT_FILE`을 certifi의 인증서 파일로 지정한다. TLS 검증을 끄지 않는다. 모든 명부 작업 파일은 `private/cbck/`에만 둔다. 이 폴더를 공개 사이트나 GitHub에 업로드하지 않는다.

클라우드 작업은 먼저 개발 프로젝트 이름/ref와 빈 스키마·기존 migration 이력을 확인한다. 0001→0002→0003→0004를 적용한 뒤 검토용 SQL을 private staging에만 넣고, 별도 읽기 쿼리로 고유 code·예약 번호·기관/시설·Auth 계정 수를 검증한다. 이미 적용된 마이그레이션을 다시 실행하거나 DB를 reset하지 않는다. 번호 충돌이 있으면 임의 재번호 대신 중단하고 원인을 검토한다. 실제 운영 데이터에는 실행하지 않는다.

`institution-auth` 개발 배포와 허용 origin·서버 salt·중앙관리자 MFA 설정이 추가로 필요하다. 비밀번호/서비스 키를 채팅이나 GitHub에 저장하지 않는다. 실제 계정 기능과 보안 검사 완료 및 사용자 승인 전 v0.21 정식 배포 금지.
