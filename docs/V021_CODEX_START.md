# CAMUM v0.21 — Codex 작업 시작 지시
기존 GitHub 저장소: https://github.com/coend01-web/gamum
현재 작업 브랜치: `feature/v0.21-convent-ops`.
**main/v0.2 공개 사이트는 건드리지 마세요.**

1. `docs/V021_BUILD_SPEC.md`를 전체 읽고 빠진 요구사항을 먼저 확인하세요. 이 기준에 따라 실제 코드까지 구현하세요. 문서만 작성하고 종료하지 마세요.
2. 기존 vanilla JS 기반 v0.2를 보존합니다. 네 가지 입구, 10문항, CAMUM, 1분 머뭄 펼침, 서랍, 수도회 시연의 기존 회귀 검사부터 실행합니다.
3. 실운영 백엔드는 Supabase(Auth, PostgreSQL, RLS, Storage, 필요한 서버 함수)를 우선 평가하고 구현합니다. **실제 배포 전에 개발용 Supabase 프로젝트가 필요하므로 계정 연결이 없으면 정확한 사용자 조치만 요청**하세요. 비밀번호·Supabase secret key/DB 암호는 채팅/GitHub에 올리지 마세요. publishable key만 프런트 코드에 가능합니다.
4. 기관이 승인 전에는 비공개 초안만 저장 가능하고 플랫폼 운영자가 승인한 뒤 공개할 수 있도록 DB 권한에서 막으세요. **수도회마다 관리번호 1개 + 공용 비밀번호 1개**로 접속하는 기관 계정 관리, 담당자 교체 시 기존 자료 유지, 비밀번호 변경·안전한 재설정·기존 세션 해제, 변경 이력. 담당자 개인별 계정은 의무화하지 말 것.
5. 수도회마다 프로그램 **무제한 다건**과 반복 회차를 등록·수정·복제·마감할 수 있어야 합니다. CSV 일괄 업로드(검증→미리보기→저장)와 모바일에서도 쉽게 쓰는 화면.
6. 프로그램/회차를 별도 테이블로 관리하고 날짜, 참가비·정원·대상·선행 자격·모집 상태·공식 신청처 모두 저장. 정원과 잔여석 허위 실시간 표기 금지. 기존 수도회 직접 입금·환불 그대로.
7. 승인된 실데이터를 주제·날짜·장소·10문항 추천과 연결하고 허위·가상 자료는 실제로 표시하지 말 것. 실제 피정이 0~2개면 임의로 3개 채우지 말 것.
8. QR 후기(현장 인증, 중복 방지, 익명 공개 시 개인정보 보호), 모집 상태·알림 등을 v0.21 운영 범위에서 구현하고 보안 검증.
9. 한 수도회 계정에서 다른 수도회의 비공개 내용을 볼 수 없고, 미승인 기관이 공개하거나 플랫폼 승인 권한을 사용할 수 없도록 RLS/접근통제 테스트. 비밀번호 변경 후 기존 세션 폐기와 재설정 기관 인증도 확인. 모바일·PC에서 기관번호+비밀번호 로그인→실제 등록→다회차 생성→공개→검색·추천→공식 신청처 이동 E2E 테스트.
10. **v0.21 정식 공개는 별도 사용자 승인 후.** 구현 후 테스트 URL, GitHub 커밋, DB 마이그레이션, 테스트 결과와 운영 계정에 필요한 클릭 조작을 초보자 눈높이로 보고하세요.
11. 수도회 전체 프로그램을 운영 가능하게 만드는 것이 v0.21의 완료 기준입니다. '1개 프로그램 등록 시범'만 지원하는 결과를 완료라고 보고하지 마세요.

실행 가능한 DB 마이그레이션의 보안은 반드시 실제 개발 프로젝트에서 검증하세요. 이번 채팅에서 제공된 ZIP에는 **SQL 초기 초안**이 있으나, 검토 없는 실서비스 배포를 금지합니다.
## 사용자 최종 결정: 개인별 로그인 방식 대신 기관 공용 계정
- 수도회마다 **관리번호 하나와 비밀번호 하나**만 사용. 담당자 교체 후에도 번호와 등록 데이터 유지.
- 기존 개인별 로그인 제안을 우선 적용하지 말고 최신 `docs/V021_BUILD_SPEC.md` 내용을 따른다.
- 계정 공유의 보안 위험을 완화하기 위해 비밀번호 변경·세션 무효화·기관 확인 후 비밀번호 재설정·중앙관리자 MFA·기관 간 데이터 격리를 구현한다.
- 공용 기관 계정에서는 개인별 작성자 확인이 불가능하므로 그 한계를 표시하고 작성·수정 시각은 기록한다.


## 장기 확장을 위한 설계 제약 (2026-11-08)
- 사용자가 후속 확장을 명시함: **사제 강사/피정 지도자 정보, 생활성가 가수·그룹과 공연/문화행사**.
- v0.21에서는 실제 수도회 운영 기능 개발에 집중. 단, 조직 모델을 수도회 전용으로 고정하지 말고 교구·본당·사도직 단체 등 운영 주체가 확장될 수 있도록 설계.
- 사제/강사/생활성가 팀/장소/행사·회차를 분리할 수 있도록 DB 참조 구조를 마련. 실제 사제 프로필·생활성가 공연 기능은 후속 버전 범위.
- 피정 추천에 생활성가 공연·성지순례 광고를 혼합하지 말 것.
- 현재 확정된 **수도회별 관리번호 1개 + 비밀번호 1개** 정책은 그대로 유지. 사제 개인·가수에게 같은 공용계정을 강요하지 않는다.
- 자세한 제약은 최신 `docs/V021_BUILD_SPEC.md` 참고.


## CBCK 공식 명부 전국 사전등록 작업 (2026-11-09)
사용자 확정 요구: 새 수도회가 신청할 때 기관명을 다시 입력하거나 다른 수도회를 선택하지 않도록 **CBCK 등재 수도회·수녀회 본부 및 피정·기도의 집을 미리 분류해 등록 후보/관리코드를 준비**한다.

1. 먼저 `docs/CBCK_DIRECTORY_PRELOAD.md`를 읽는다. 전체 CBCK 목록 자동 감사는 성공(남자 224/224, 여자 500/500, 피정·기도의 집 190/190, 본부 후보 남자 50/50·여자 112/112).
2. `scripts/prepare_cbck_catalog.py`와 `scripts/export_cbck_staging_sql.py`를 실행. CSV 및 SQL은 `private/cbck/` 에만 두고 공개 GitHub에 커밋하지 않는다.
3. 예비 기관 관리번호 162개, 피정시설번호 190개를 만들되 실제 수도회 본부·관구·분원 중복과 관리권한을 확인할 때까지 활성화하지 않는다. CBCK 주소록 등재만으로 가뭄과 제휴 또는 운영 동의를 받았다고 표시하면 안 된다.
4. 개발 Supabase에 0001→0002→0003 마이그레이션과 권한 검증 후 **비공개 원천 staging 테이블**에만 검토용 SQL을 반영한다. 기존 공개 v0.2/main은 변경하지 않는다.
5. 실제 기관은 승인 후 기존 예약 번호를 사용하고, 본인 확인 후 **기관 공용 비밀번호를 처음 설정**한다. 비밀번호를 일괄 생성하거나 모두 같은 기본 비밀번호를 만들지 않는다.
6. 피정의 집은 추정으로 특정 수도회에 연결하지 말고 운영 주체 확인 후 매칭한다. 교구 직영 시설이 포함됨.
7. 914개 고유 CBCK 등재 항목과 본부 후보 162개 분류를 사용자가 확인할 수 있는 중앙 관리자 검색·검수 화면의 원천 데이터로 삼는다. 출처/확인일/승인 상태 표시.
